About HTTP Status Codes

An HTTP status code is the three-digit number in the first line of every response. It tells the client, and anything in between such as a CDN, a load balancer or a cache, whether the request worked, needs another step, or failed and on which side. The codes are defined in RFC 9110, section 15 (HTTP Semantics, which replaced RFC 7231 and the older RFC 2616). Extensions such as 429, 431 and 451 come from their own RFCs. The authoritative list is the IANA HTTP Status Code Registry. This reference follows that registry and labels everything outside it as non-standard.

The Five Classes

  • 1xx Informational: an interim response; the final one follows. You see 100 Continue with large uploads, 101 Switching Protocols on WebSocket upgrades and 103 Early Hints on sites that preload assets.
  • 2xx Success: the request was received, understood and accepted. 200 OK is the default; 201 Created, 204 No Content and 206 Partial Content each mean something specific.
  • 3xx Redirection: the client has to do something else, usually follow the Location header. 301 and 308 are permanent, 302, 303 and 307 are temporary, and 304 Not Modified says the cached copy is still valid.
  • 4xx Client error: the server blames the request: bad syntax, missing credentials, no permission, wrong URL, too large or too many. Sending the same request again will not help.
  • 5xx Server error: the request looked valid but the server, or a proxy in front of it, failed. Retrying with back-off is often reasonable, especially for 502, 503 and 504.

Clients that meet an unknown code must treat it like the x00 code of its class. A client that does not know 429 handles it like 400, for example. That rule is why vendors can invent codes such as 499 or 520 without breaking browsers.

How to Check a Status Code with curl

The browser hides most of what matters: redirects, caching headers and which hop produced the error. Use curl instead:

# Status line + headers (HEAD request)
curl -I https://example.com/

# Exact status of a normal GET, nothing else
curl -s -o /dev/null -w '%{http_code}\n' https://example.com/

# Follow the redirect chain and show every hop
curl -sIL http://example.com/ | grep -iE '^(HTTP|location)'

# Timing breakdown: which phase is slow?
curl -s -o /dev/null -w 'code=%{http_code} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://example.com/

# Bypass the CDN / load balancer and hit one origin directly
curl -svk --resolve example.com:443:203.0.113.10 https://example.com/ -o /dev/null

-I sends HEAD, and some frameworks route HEAD differently or return 405 for it. When the result looks odd, repeat it with a real GET using -o /dev/null -w. --resolve keeps the correct SNI and Host header while pinning the IP address, which is the cleanest way to tell an edge problem from an origin problem.

Which Hop Generated the Error?

Most production outages show up as a 5xx that your application never produced. Read the response before you read the application logs. A Server header of cloudflare combined with a 52x code means Cloudflare's edge could not get a usable answer from your origin. An nginx-branded error page means the reverse proxy gave up on its upstream, and the nginx error.log names the reason: upstream timed out gives 504, no live upstreams or upstream prematurely closed connection gives 502. On an AWS Application Load Balancer, compare the HTTPCode_ELB_5XX_Count metric (generated by the load balancer) with HTTPCode_Target_5XX_Count (returned by your targets). Work from the outside in: edge, load balancer, reverse proxy, application server, database.

Redirects: 301 vs 302 vs 303 vs 307 vs 308

CodePermanent?Method preserved?Typical use

302NoNo, POST may become GETLogin redirects, short-lived moves
303NoAlways becomes GETPost/Redirect/Get after a form submit
307NoYesTemporary moves of API endpoints
308YesYesPermanent moves of APIs and non-GET traffic

Browsers cache permanent redirects hard. Test a new redirect with a 302 or 307 first, and switch to 301 or 308 once the target is right.

Retry or Not?

Retry 408, 429, 502, 503 and 504 with exponential back-off, and honour Retry-After when it is present. Do not retry most other 4xx codes, because the request itself is wrong. Cloudflare's own guidance treats 525 and 526 as not retryable until someone fixes the origin's TLS configuration. Only repeat non-idempotent requests (POST) automatically if the API offers idempotency keys.

Non-Standard Codes

Codes tagged non-standard in the list are not in the IANA registry. They come from one vendor and mean nothing outside that vendor's products. nginx uses 444, 494–497 and 499 internally; 494–497 reach the client as a plain 400 with a specific error page. Cloudflare's edge generates 520–526. The AWS Application Load Balancer adds 460, 463 and 464. Search for the vendor name (nginx, cloudflare, aws) to list them.
