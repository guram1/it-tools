How tunnel MTU and TCP MSS are calculated

            
Every encapsulation adds bytes in front of (and sometimes behind) the original packet, but the underlay link still carries at most its MTU. The inner IP MTU is the largest original IP packet that still fits after encapsulation, and the TCP MSS is that MTU minus the fixed inner IP header (20 bytes for IPv4, 40 for IPv6) and the 20-byte TCP header. RFC 6691 says the MSS should be reduced only by the fixed IP and TCP headers, not by options, so timestamps and SACK do not change the value you clamp to.

            
For GRE, VXLAN and WireGuard the overhead is a constant, so subtraction is enough. ESP is different: the encrypted part (payload + padding + 2-byte trailer) must be a multiple of the cipher block size and must end on a 4-byte boundary (RFC 4303 §2.4). The padding, and so the overhead, changes with the size of the packet. This calculator does not assume a "typical" ESP overhead. It builds the packet layer by layer for every candidate size and returns the largest inner packet whose encapsulated size is still ≤ the underlay MTU.


            
Overhead sources used

            
    
                
  • Outer IP header: 20 bytes IPv4, 40 bytes IPv6 (no options or extension headers).
    • 
                
  • ESP header: SPI 4 + sequence number 4 (RFC 4303). With Extended Sequence Numbers the high-order 32 bits are not transmitted, so ESN adds nothing on the wire.
    • 
                
  • IV: 16 bytes for AES-CBC (RFC 3602), 8 bytes for AES-GCM (RFC 4106).
    • 
                
  • Padding: 0–15 bytes for AES-CBC (16-byte blocks), 0–3 bytes for AES-GCM (4-byte alignment only), plus the 2-byte Pad Length / Next Header trailer.
    • 
                
  • ICV: HMAC-SHA1-96 = 12 (RFC 2404), HMAC-SHA-256-128 = 16, SHA-384-192 = 24, SHA-512-256 = 32 (RFC 4868, truncated to half the hash output); the AES-GCM tag is 16 by default, 8 or 12 optional (RFC 4106 §6).
    • 
                
  • NAT-T: 8-byte UDP header, port 4500 (RFC 3948).
    • 
                
  • GRE: 4-byte base header (RFC 2784), +4 each for checksum, key and sequence number (RFC 2784 / RFC 2890).
    • 
                
  • VXLAN: UDP 8 + VXLAN 8 + the inner Ethernet header 14 (18 with an 802.1Q tag) (RFC 7348). The outer Ethernet header is not part of the IP MTU.
    • 
                
  • WireGuard: UDP 8 + 16-byte data header (type, reserved, receiver index, 64-bit counter) + 16-byte Poly1305 tag (WireGuard whitepaper §5.4.6).
    • 
                
  • MPLS: 4 bytes per label stack entry (RFC 3032), counted against the underlay MTU.
    • 
            


            
Worked example: AES-CBC + HMAC-SHA-256, ESP tunnel mode, 1500-byte IPv4 underlay

            
Fixed bytes: outer IPv4 20 + ESP header 8 + IV 16 + ICV 16 = 60. That leaves 1440 bytes for the encrypted block, and 1440 is exactly 90 AES blocks. Payload + padding + 2 must equal 1440, so the largest inner packet is 1438 with zero padding: 20 + 8 + 16 + 1438 + 0 + 2 + 16 = 1500. A 1439-byte packet needs 1441 encrypted bytes, which rounds up to 1456, and the result is a 1516-byte packet that no longer fits. The MSS is 1438 − 40 = 1398 for IPv4 and 1438 − 60 = 1378 for IPv6.

            
Padding can make the result look wrong at first. Add NAT-T and the budget becomes 1432. The largest multiple of 16 that fits is 1424, so the inner MTU drops to 1422. On a 1492-byte PPPoE link without NAT-T the budget is also 1432, so the answer is again 1422: ten bytes less underlay MTU gives the same tunnel MTU. With AES-GCM the alignment is only 4 bytes, so the same 1500-byte link gives 1446 (1438 with NAT-T).

Cisco's GRE/IPsec fragmentation guide lists 1440 (transport mode) and 1420 (tunnel mode) as the specific MTU needed on a 1500-byte link and recommends 1400 for both. AES-CBC with SHA-256 needs slightly less (1434 / 1414) because of its 16-byte IV and block padding, which is why many engineers use the round 1400 / MSS 1360 and accept a few unused bytes. Use the safety-margin field if you want to standardise on a value like that.


            
Vendor notes

            
    
                
  • Cisco IOS / IOS XE: ip mtu on the tunnel interface sets the IP MTU. Cisco's command reference documents ip tcp adjust-mss with a range of 500–1460 and notes that it affects only TCP connections passing through the router. For IPv6 the equivalent is ipv6 tcp adjust-mss. By default the GRE tunnel ip mtu is the physical MTU minus the GRE overhead only, so with tunnel protection you must lower it yourself.
    • 
                
  • FortiOS: on a route-based IPsec tunnel interface, set mtu-override enable, set mtu and set tcp-mss take precedence over the per-policy tcp-mss-sender / tcp-mss-receiver values (Fortinet technical tip). Both default to 0 in the FortiOS CLI reference. Set both of them.
    • 
                
  • Junos: family inet mtu is the IP MTU. The physical (media) MTU includes the Layer 2 header (1514 for standard Ethernet), so do not copy IP MTU values into the physical mtu statement. On SRX, set security flow tcp-mss ipsec-vpn mss clamps traffic entering IPsec. gre-out applies to GRE going into an IPsec tunnel and gre-in to GRE coming out of one. Juniper warns that MSS may not be rewritten for GRE over IPsec, so verify with a packet capture.
    • 
                
  • WireGuard: wg-quick sets the interface MTU to the route MTU minus 80, the IPv6-underlay worst case. That gives the familiar 1420. The 16-byte zero padding is capped at the interface MTU by the Linux implementation, so it never pushes a full-size packet over the limit.
    • 
                
  • VXLAN: RFC 7348 says VTEPs must not fragment VXLAN packets. The normal fix is to raise the underlay MTU (for example 9000/9216 in the fabric) rather than shrink the tenant MTU to 1450.
    • 
            


            
Common mistakes

            
    
                
  • Forgetting NAT-T. A tunnel that worked on a public IP loses 8 bytes when one peer moves behind NAT. Size for NAT-T if it can ever happen.
    • 
                
  • Using the IPv4 MSS for IPv6. IPv6 needs an MSS 20 bytes lower. A tunnel under 1280 bytes cannot carry IPv6 at all.
    • 
                
  • Treating MSS clamping as a full fix. Clamping rewrites only TCP SYNs. UDP, QUIC, GRE keepalives and nested VPNs still depend on a correct tunnel MTU and working PMTUD. Do not block ICMP "fragmentation needed" (type 3 code 4) or ICMPv6 Packet Too Big.
    • 
                
  • Stacking PPPoE and a VPN without recalculating. Start from 1492, not 1500, on PPPoE links.
    • 
                
  • Clamping in one direction only. Each TCP endpoint advertises its own MSS in its SYN or SYN-ACK. If only one of them is rewritten, the other side can still send full-size segments into the tunnel. On FortiOS set both tcp-mss-sender and tcp-mss-receiver, and on any platform confirm with a capture that both SYN and SYN-ACK leave with the clamped value.
    • 
            


            

                
Frequently Asked Questions

                
ESP pads the encrypted part (payload, padding and the 2-byte trailer) to a multiple of the cipher block size and to a 4-byte boundary (RFC 4303). With AES-CBC the padding is 0 to 15 bytes, so the overhead changes with packet size. With AES-GCM it is 0 to 3 bytes. The calculator searches for the largest inner packet whose encapsulated size still fits the underlay MTU instead of subtracting an average.

                
MSS = inner MTU minus the fixed inner IP header and the 20-byte TCP header: MTU minus 40 for IPv4 and MTU minus 60 for IPv6. RFC 6691 says TCP and IP options should not be subtracted, so the value does not change when timestamps or SACK are in use.

                
Transport mode protects the GRE packet and reuses its delivery IP header, so it saves 20 bytes with an IPv4 underlay and 40 with IPv6. Tunnel mode adds a second outer IP header. Use transport mode when the GRE endpoints are the IPsec peers. Behind NAT, check that your platform supports transport mode with NAT-T.

                
Yes. When a NAT is detected, ESP is carried in UDP port 4500 (RFC 3948), which adds an 8-byte UDP header to every packet. Because of AES-CBC block padding, those 8 bytes can cost up to 16 bytes of inner MTU. For example, AES-CBC with SHA-256 drops from 1438 to 1422 on a 1500-byte link.

                
wg-quick sets the interface MTU to the underlay MTU minus 80 bytes: a 40-byte IPv6 header, 8 bytes UDP, a 16-byte data header and a 16-byte Poly1305 tag. That value is safe for IPv4 and IPv6 endpoints. With an IPv4-only underlay the real limit is 1440 on a 1500-byte link.
