                        FortiOS version notes (7.2 / 7.4 / 7.6)
                        
    
                            
  • 7.2 and 7.4: CLI defaults for phase1-interface are ike-version 1 and dhgrp 14. Omitting them silently gives you IKEv1.
    • 
                            
  • 7.6: the CLI default is still ike-version 1; the documented phase1/phase2 dhgrp default changed to 20 (Fortinet marks it as model-dependent). The GUI VPN wizard defaults to IKEv2 from 7.6.0.
    • 
                            
  • All three: net-device defaults to disable and peertype defaults to peer (certificate), so the builder sets peertype any for PSK, as in Fortinet's examples. Phase1 AES-GCM / ChaCha20 proposals require IKEv2.
    • 
                            
  • The builder sets ike-version, proposal and dhgrp explicitly on both sides, so the result does not depend on version defaults. Check get system status and the CLI reference for your exact build.
    • 
                        

                    

                

            

        


        

            
What this FortiGate CLI builder does

            
Most FortiGate changes that take an hour in the GUI take a minute in the CLI, provided the syntax is right. This builder produces FortiOS CLI for the two jobs network engineers repeat most: importing a list of addresses as config firewall address objects with a matching config firewall addrgrp, and building a route-based site-to-site IPsec VPN between two FortiGates. The output is plain text you paste into the CLI console, an SSH session or a FortiManager CLI script. Nothing is sent to a server.


            
Mode 1: bulk address objects

            
Each input line is classified and mapped to the matching address type from the FortiOS CLI reference:

            
    
                
  • Single IP or CIDR (10.10.5.20, 10.20.0.0/16, 10.20.0.0 255.255.0.0) becomes set type ipmask with set subnet <ip> <mask>. A bare IP is a /32 host. ipmask is the default type, but it is written explicitly so the intent is visible in reviews.
    • 
                
  • Range (192.168.50.10-192.168.50.40) becomes set type iprange with set start-ip and set end-ip. Both ends are inclusive.
    • 
                
  • FQDN (updates.example.com, *.example.com) becomes set type fqdn with set fqdn. Wildcard FQDNs use the same type; Fortinet documents that the FortiGate must see the client's DNS traffic for wildcard objects to populate.
    • 
            

            
Text after # becomes set comment. Quotes and backslashes are stripped from comments because the FortiOS CLI treats them as special characters. CIDRs with host bits set (for example 10.1.1.5/24) are rejected rather than silently rounded, because a typo in a mask usually means the source list is wrong. The tool also flags entries that overlap each other: if 10.20.30.0/24 is already inside 10.20.0.0/16, you probably do not need both objects in the same group.


            
Worked example: addresses

            
The line 10.20.0.0/16 # Branch LAN with prefix ACME_ produces:

            
config firewall address
    edit "ACME_n-10.20.0.0_16"
        set type ipmask
        set subnet 10.20.0.0 255.255.0.0
        set comment "Branch LAN"
    next
end

            
If you fill in a VDOM, the block is wrapped in config vdom / edit <vdom> … next / end, which is how Fortinet's multi-VDOM examples enter a VDOM context. On a FortiGate without multi-VDOM mode, leave the field empty.


            
Mode 2: route-based site-to-site IPsec VPN

            
The VPN mode writes both ends at once, so the proposals, DH groups and selectors match by construction. For each side it produces, in dependency order: address objects and two address groups (<tunnel>_local, <tunnel>_remote), config vpn ipsec phase1-interface, config vpn ipsec phase2-interface, a static route plus a blackhole route per remote subnet, and an outbound and inbound firewall policy. Objects must exist before anything references them, so paste the output top to bottom.

            
The phase1 uses set interface (WAN), set ike-version, set peertype any, set net-device disable, set proposal, set dhgrp, set remote-gw and set psksecret, the same keywords as Fortinet's site-to-site examples. Tunnel names are limited to 15 characters because the phase1-interface name becomes an interface name. Static routes and policies use edit 0, which tells FortiOS to assign the next free sequence number instead of overwriting an existing entry.


            
Worked example: VPN

            
Site A, WAN wan1 at 203.0.113.10, protects 10.10.0.0/24 and 10.10.10.0/24. Site B, WAN wan1 at 198.51.100.20, protects 10.20.0.0/16. In "one phase2 per subnet pair" mode, Site A gets two phase2 entries (10.10.0.0/24 ↔ 10.20.0.0/16 and 10.10.10.0/24 ↔ 10.20.0.0/16), one route to 10.20.0.0 255.255.0.0 via the tunnel and one blackhole at distance 254 for the same prefix. Site B gets the mirror image: two routes and two blackholes. With IKEv2, aes256gcm-prfsha384 and DH 20 in phase1, and aes256gcm with PFS group 20 in phase2, both sides negotiate the same suite on the first proposal.


            
Why the blackhole route matters

            
A route-based tunnel installs its static route only while the tunnel interface is up. When the peer goes down, traffic for the remote subnets falls through to the default route and leaves the WAN unencrypted. A blackhole route for the same prefixes at administrative distance 254 is ignored while the tunnel route (distance 10 by default) is present and drops the traffic when it is not. It also helps when the remote subnets are RFC 1918 space you should never send to an ISP.


            
Selector strategy and interoperability

            
    
                
  • One phase2 per pair uses src-subnet/dst-subnet. It is verbose, but it matches what Cisco, Palo Alto, Check Point and cloud VPN gateways configured with explicit traffic selectors expect.
    • 
                
  • Address-group selectors (src-addr-type name, dst-addr-type name) are what the FortiOS 7.6 VPN wizard generates. They are compact and fine between FortiGates; confirm support on the peer before using them with other vendors.
    • 
                
  • 0.0.0.0/0 selectors negotiate a single SA and leave traffic control to routing and policy. Use them FortiGate-to-FortiGate or with route-based (VTI) peers, not with policy-based crypto maps.
    • 
            


            
Common mistakes this tool prevents

            
    
                
  • Relying on defaults: the phase1 CLI default is IKEv1 on 7.2, 7.4 and 7.6, and the default DH group differs between versions. The builder always writes them out.
    • 
                
  • Mismatched proposals: phase1 AES-GCM and ChaCha20 suites are IKEv2-only on FortiGate, so the tool blocks them with IKEv1.
    • 
                
  • Overlapping local and remote subnets: these need NAT and cannot be routed as-is, so they are reported as errors.
    • 
                
  • PSKs with ?: the FortiGate CLI uses ? for help, and Fortinet notes that question marks cannot be pasted into the CLI console or some SSH clients. Generated keys use letters and digits only (40 characters, about 238 bits of entropy).
    • 
                
  • Forgetting the policy direction: two policies are generated, LAN → tunnel and tunnel → LAN, both with set nat disable, because source-NATing site-to-site traffic breaks return routing and logging.
    • 
            


            
Verify after pasting

            
Bring the tunnel up and check it with diagnose vpn ike gateway list name <tunnel> and diagnose vpn tunnel list. For negotiation failures, run diagnose debug application ike -1 with diagnose debug enable; a "probable pre-shared secret mismatch" message points at the PSK. Confirm routing with get router info routing-table static. To roll back, delete the policies first, then the routes, phase2, phase1 and finally the address objects, the reverse of the creation order.
